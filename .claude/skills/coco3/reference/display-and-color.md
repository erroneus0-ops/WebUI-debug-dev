# CoCo 3 display modes and the 64-color palette

Full color table:
`../../coco/reference/xls-conversion/reference-tabs/coco-3-colors.csv`
(64 rows, RGB and CMP/composite index side by side, with color name).
Register addresses controlling mode/resolution/border:
`gime.md` (`$FF98`-`$FF9A`).

## How the palette works

The CoCo 3 exposes 64 colors, split across two monitor types with
**different numeric indices for the same visual color** — the table
maps between them so you can target either. Sample rows (RGB index, CMP
index, name):

| RGB | CMP | Color |
|---|---|---|
| 00 | 00 | Black |
| 01 | 12 | Low intensity blue |
| 02 | 02 | Low intensity green |
| 07 | 16 | Low intensity white |
| 09 | 44 | Full intensity blue |
| 18 | 18 | Full intensity green |
| 36 | 39 | Full intensity red |
| 45 | 41 | Full intensity magenta |

**Practical rule, stated directly in the original documentation:** decide
the color you want, find it in the table, then use the RGB index if
targeting an RGB monitor or the CMP index if targeting a composite
monitor/TV — the two numbers are *not* interchangeable even though they
name the same visual color, because RGB and composite colors are
generated by genuinely different underlying methods. Using the wrong
column's index against the wrong monitor type produces the wrong color,
not just a slightly-off one.

## Display mode registers — genuinely different mechanism, not just a
tidier version of the SAM

`$FF98` (Video Mode) sets text-vs-graphics (`BP` bit) and a **Lines Per
Row (`LPR`)** value directly — bits 2-0 of the register are written as a
literal 3-bit row-count selector, looked up in a table:

```
LPR bits   Text mode rows   Graphics mode rows
   000            1                 1
   010            2                 2
   011            8                 7
   100            9                 8
   101           10                 9
   110           11                10
   111        infinite           infinite
```

**This is the key structural difference from the CoCo 1/2 SAM/VDG pair**
(see the **coco** skill's `hardware-io.md`): on CoCo 1/2, "how many
scanlines share one fetched byte" is an *emergent side effect* of the
SAM's address-timing divisor — the free-running row counter and the
fetch-timing divisor are two independent things that happen to interact.
On the CoCo 3, GIME's `LPR` is a **direct, deliberately-chosen register
value** — text and graphics modes even get genuinely different row-count
tables for the same bit pattern, which is not how the SAM works at all.

**Open question, not yet verified either way:** whether GIME's own row
counter shares the SAM's "keeps running regardless of actual fetch
timing" property that causes CoCo 1/2's mid-character text-slicing
artifact (see `hardware-io.md`'s free-running-row explanation). The more
direct, deliberate design here suggests that specific artifact may not
reproduce the same way on CoCo 3 — but that's a reasoned guess, not
something traced through GIME's actual implementation. Don't assume
either way without checking.

## Third-party GIME replacements (GIME-X, GIME-Z)

Real, physical, purchasable FPGA-based replacement chips for a CoCo 3's
GIME socket — not emulation projects:

- **GIME-X** — Gary Becker + "Zippster," documented at
  thezippsterzone.com. Adds NTSC/composite/s-video output, support for
  >512K memory, and new video modes (640×225-16 color, 320×225-256 color,
  640×112-256 color) beyond anything stock GIME supports. Also adds a new
  register at `$FFEF` ("GIME-X information byte") with version bits and a
  memory-type flag, useful for detecting real/emulated stock GIME vs.
  GIME-X specifically at runtime.
- **GIME-Z** — a separate project ("AC's 8-bit Zone," sold via
  cocobits.org). Confirmed to exist as a real distinct product; detailed
  feature-by-feature documentation not yet located to the same depth as
  GIME-X's.

**Not yet confirmed either way:** whether GIME-X/GIME-Z improve
semigraphics (SG4-24) *fidelity* specifically, versus just adding new
graphics modes/resolutions alongside stock GIME's existing repertoire.
Don't assume a fix for one implies the other.

## Relationship to the CoCo 1/2 SG12 hack

The **coco** skill documents an undocumented CoCo 1/2 semigraphics mode
(SG12) reached via specific SAM `V`-bit combinations. The CoCo 3's GIME
provides its own richer set of *documented* graphics modes at
comparable or better resolution/color depth — when porting code that
relies on SG12 specifically for its CoCo 1/2 compatibility, check
whether a genuine CoCo-3-native mode via `$FF98`/`$FF99` better serves
the same visual goal, rather than assuming SG12 itself is the only path
forward on CoCo 3 hardware (real hardware compatibility mode aside).
